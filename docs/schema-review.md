# UEMP Schema for Review

**Status** · Approved for implementation

The schema covers student registration and academic history, lecturer grading, departmental approval, and university administration. A course can appear in several programmes while each department controls its own delivery and results. An admin who teaches an offering can also approve its results when an assignment gives that admin approval privileges in the offering’s department.

## Naming and common fields

PostgreSQL uses `snake_case` for tables, columns, and named constraints. NestJS uses singular entity names and `camelCase` properties. The field tables below use NestJS property names. An unmarked field is required. “Optional” means the column is nullable. “Reference” means a UUID foreign key to the named entity.

| Property | Type and default | Comment |
| --- | --- | --- |
| `id` | UUIDv7, primary key | Gives each record a stable ID generated by the application. |
| `createdAt` | Timestamp with time zone, defaults to now | Records when the row was created. For a matriculation record, this is also the issuance timestamp. |
| `updatedAt` | Timestamp with time zone, defaults to now | Records the most recent edit to a mutable row. |

Every PostgreSQL entity has `id`. Mutable entities have both timestamps. `AdminRole`, `CourseOfStudyCourse`, and `MatricNumSystem` have `createdAt` only. `AdminAudit` uses `occurredAt` for its event time.

## Accounts and privileges

### User

PostgreSQL table `users`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `firstName` | Text, optional | Stores the given name used on the user’s profile and in display names. |
| `lastName` | Text, optional | Stores the family name used on the user’s profile and in display names. |
| `role` | `student` or `admin` | Identifies the account type used to sign in and selects the corresponding profile. |
| `email` | Text | Stores the trimmed, lowercase login address. It is unique within an account type. On deletion, a unique placeholder replaces the original address. |
| `hashedPassword` | Text, nullable for deleted accounts | Stores the password hash used to verify sign-in. Account deletion clears it. API responses, logs, and audit records exclude it. |
| `authVersion` | Nonnegative integer, defaults to `0` | Identifies the current token family. Issuance, rotation, and account revocation advance it so older tokens fail validation. |
| `deletedAt` | Timestamp with time zone, optional | Records when account access ended and its identity was redacted. The internal ID remains available to academic and audit records. |
| `status` | `active` or `suspended`, defaults to `active` | Controls whether the account can authenticate and continue an existing session. |

Enforce uniqueness on `(email, role)`. A deleted row retains its placeholder address, so its former address can be registered again within the same account type. Account creation writes the matching profile in the same transaction. The account type is fixed after creation. Sign-in identifies the account type and rejects suspended or deleted users. Changing the password, suspending the account, or deleting it invalidates the active session.

### Student

PostgreSQL table `students`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `userId` | Reference to User, unique | Connects the academic profile to exactly one Student account. |
| `academicLevelId` | Reference to AcademicLevel, optional, sets null on deletion | Holds the current level. A student can choose a valid level during signup. Later changes require an authorized admin. |
| `courseOfStudyId` | Reference to CourseOfStudy, optional, sets null on deletion | Identifies the student’s programme. Its course links define which catalog courses the student can take. |
| `departmentId` | Reference to Department, optional, sets null on deletion | Records the current department for administration and access checks. It also supports placement before a programme is chosen. |
| `facultyId` | Reference to Faculty, optional, sets null on deletion | Records the current faculty and identifies its selected registration semester. It also supports placement before a department is chosen. |

The one-to-one `matricNumSys` relation is populated from `MatricNumSystem.studentId`. Validate each placement change as a single operation. A selected programme must belong to the selected department, the department must belong to the selected faculty, and the level’s programme type must match the programme’s type when both are set. Registration requires a complete, active placement and an issued matriculation number. Placement changes affect future eligibility. Semester records preserve their original context. The matriculation number survives placement changes and is removed on account deletion.

### Admin

PostgreSQL table `admins`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `userId` | Reference to User, unique | Connects the administrative profile to exactly one Admin account. |
| `createdByAdminId` | Reference to Admin, optional, sets null on deletion | Identifies the admin who created this account. The bootstrap account can start without a creator. |

The `adminRoles` collection comes from `AdminRole.adminId`. Role changes keep the same Admin ID, so a lecturer can become HOD and continue to own the relevant teaching and audit records.

### Role

PostgreSQL table `roles`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `name` | Text, normalized to lowercase, unique | Names the role, such as `hod`, `lecturer`, or `ict-manager`. Admin assignments read this name from the linked role. |
| `description` | Text, optional | Explains what the role is for when an administrator reviews or assigns it. |
| `kind` | `custom` or `system` | Distinguishes administrator-defined roles from the roles seeded by the application. |
| `systemKey` | `super_admin`, `hod`, or `lecturer`, optional, unique when set | Gives each seeded role a stable identifier independent of its display name. A system role requires a key and a custom role has none. |
| `createdByAdminId` | Reference to Admin, optional, sets null on deletion | Records the author of a custom role. Seeded roles have no creating admin. |
| `privileges` | Text array, defaults to empty | Lists capabilities such as `read_user`, `grade_result`, and `approve_result`. Values must come from the privilege catalog. |

The `adminRoles` collection comes from `AdminRole.roleId`. System keys and the capabilities of seeded roles are maintained by the application. Custom roles can combine capabilities without introducing a new user account type.

### AdminRole

PostgreSQL table `admin_roles`. Each row grants a named role to an admin, optionally within one department. Read the name through `roleId`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `adminId` | Reference to Admin, cascades on deletion | Identifies the administrator receiving the role. |
| `roleId` | Reference to Role, cascades on deletion | Identifies the role whose privileges the assignment grants. |
| `assignedByAdminId` | Reference to Admin, optional, sets null on deletion | Identifies the admin who granted the role. Bootstrap assignments may have no assigner. |
| `departmentId` | Reference to Department, optional, restricts deletion while assigned | Limits every privilege from this grant to one department. A null value leaves this grant without a department restriction. |

Allow the same role in different departments. Enforce one assignment for each `(adminId, roleId, departmentId)`, treating null department values as equal for this check. Resolve each privilege against the target department on the individual grant. HOD privileges in one department and teaching privileges in another remain separate. A delegated grant must fit within the assigner’s privileges and scope. When creating a lecturer account, a department-scoped HOD can grant the seeded Lecturer role in that HOD’s own department. The Super Admin bootstrap assignment is explicitly university-wide. Scope changes are recorded as a revocation and a new grant.

## Academic structure and terms

### AcademicLevel

PostgreSQL table `academic_levels`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `programType` | `undergrad`, `postgrad`, `masters`, or `doctorate` | Identifies the university programme family. It must match the selected programme’s type. |
| `stage` | Integer from 0 to 6 | Records progression within the programme. Positive values are stages of study. Stage 0 records graduation. |
| `displayName` | Text, up to 100 characters | Supplies the label shown in selectors and reports. Examples are `100 Level`, `Masters`, and `Graduate`. |
| `status` | `active` or `inactive`, defaults to `active` | Controls whether this level can be selected for placement. Offerings and registrations require an active positive stage. |

Enforce uniqueness on `(programType, stage)`. Keep the programme family and stage stable after creation. Historical registrations keep their level reference after deactivation.

| Programme family | Seeded stages and display names |
| --- | --- |
| `undergrad` | Stages 1–6 use `100 Level` through `600 Level`. |
| `postgrad` | Stage 1 uses `Postgraduate`. |
| `masters` | Stage 1 uses `Masters`. |
| `doctorate` | Stage 1 uses `Doctorate`. |

Each family has its own stage 0 row with the display name `Graduate`. In selectors that mix families, qualify this label with the family, such as `Undergraduate · Graduate`. Sort the graduate stage after the numbered stages in its family. Signup accepts active study stages. An authorized admin can assign the Graduate stage when updating an existing placement.

### AcademicSession

PostgreSQL table `academic_sessions`. The display label is derived from the year pair, such as `2026/2027`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `startYear` | Four-digit integer | Records the first calendar year of the academic session and gives sessions a chronological sort key. |
| `endYear` | Four-digit integer | Records the final calendar year of the session. It must be at least `startYear`. |
| `status` | `active` or `inactive`, defaults to `inactive` | Controls whether the session is available for current academic operations. Historical records remain linked. |

Enforce uniqueness on `(startYear, endYear)`. A session can contain multiple semesters. Faculties choose their current semester independently.

### Semester

PostgreSQL table `semesters`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `academicSessionId` | Reference to AcademicSession | Groups this semester with the other terms in the same academic year. Replaces the original `session` text field with a relation. |
| `termNumber` | Positive small integer | Orders terms within a session and gives each term an identity independent of its display name. |
| `name` | Text | Displays the semester name, such as “First Semester”. |
| `maxUnits` | Positive small integer | Caps the total units a student can register for in this semester. Changes apply when checking later registrations. |
| `status` | `active` or `inactive`, defaults to `inactive` | Controls whether the term is eligible for new registrations. Old registrations and results remain available to authorized readers. |

Enforce uniqueness on `(academicSessionId, termNumber)`. New registrations require an active session and semester and the semester must match the student’s faculty’s current selection. Lowering the unit limit leaves existing enrollments in place and applies the new limit to additional registrations.

### Faculty

PostgreSQL table `faculties`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `name` | Text, unique after case normalization | Names the faculty in the academic hierarchy and university reports. |
| `status` | `active` or `inactive`, defaults to `active` | Controls whether the faculty can be used in new placements and registrations. |
| `currentSemesterId` | Reference to Semester, optional | Selects the term open for registration in this faculty. A faculty can exist before it selects a term. |
| `shortId` | Positive database-generated integer, unique, immutable | Supplies the faculty segment of a matriculation number. The public number remains stable if the faculty is renamed. |

Only an active semester in an active session can be selected as current. Registration checks current status again at the time of enrollment.

### Department

PostgreSQL table `departments`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `facultyId` | Reference to Faculty, cascades on deletion | Places the department under its faculty and gives it the faculty’s registration semester. |
| `name` | Text | Names the department within its faculty. |
| `status` | `active` or `inactive`, defaults to `active` | Controls whether the department can be used in new placements, offerings, and registrations. |
| `shortId` | Positive database-generated integer, unique, immutable | Supplies the department segment of a matriculation number. |

Enforce uniqueness on the normalized name within each faculty. Department IDs are the boundaries for course administration and scoped privileges. A department with assigned grants, issued matriculation numbers, or academic history is deactivated in place.

### CourseOfStudy

PostgreSQL table `courses_of_study`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `departmentId` | Reference to Department | Identifies the department that administers the programme and its curriculum. |
| `name` | Text | Displays the programme name within its department, such as “BSc Computer Science”. |
| `programType` | `undergrad`, `postgrad`, `masters`, or `doctorate` | Ties the programme to valid levels from the same university programme family. |
| `status` | `active` or `inactive`, defaults to `active` | Controls whether the programme can be chosen for new placements and registrations. |
| `shortId` | Positive database-generated integer, unique, immutable | Supplies the programme segment of a matriculation number. |

Enforce uniqueness on the normalized programme name within each department. The department link remains stable for a programme with academic history.

### Course

PostgreSQL table `courses`. This is the shared course catalog.

| Property | Type and default | Comment |
| --- | --- | --- |
| `name` | Text | Gives the catalog course its display title. |
| `code` | Text, unique after normalization | Identifies the catalog course across programmes and departments. Store one canonical form, such as `CSC101`. |
| `units` | Positive small integer | Defines the catalog credit value. An offering copies this value when it is created. |
| `status` | `active` or `inactive`, defaults to `active` | Controls whether this catalog course can be used for new curriculum links, offerings, and registrations. |

The original course’s level, lecturer, and semester belong to `CourseOffering`. One catalog course can run in multiple terms or departments without changing its identity.

### CourseOfStudyCourse

PostgreSQL table `course_of_study_courses`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `courseOfStudyId` | Reference to CourseOfStudy | Identifies the programme whose curriculum includes the course. Its department governs changes to this link. |
| `courseId` | Reference to Course | Identifies the shared catalog course that students in the programme may take when offered at their level and in their current term. |

Enforce uniqueness on `(courseOfStudyId, courseId)`. This is the programme-to-course many-to-many relation. Removing a link changes future eligibility. Existing registrations keep their original programme and course references.

### CourseOffering

PostgreSQL table `course_offerings`. One offering is a department’s delivery of a course at a particular level and in a particular term.

| Property | Type and default | Comment |
| --- | --- | --- |
| `courseId` | Reference to Course | Selects the shared catalog course being delivered. |
| `departmentId` | Reference to Department | Identifies the department responsible for the roster, teaching assignment, and approval. Programmes in another department use their own offering of the same catalog course. |
| `semesterId` | Reference to Semester | Identifies the term in which this delivery takes place. |
| `academicLevelId` | Reference to AcademicLevel | Identifies the level eligible to register for this delivery. |
| `lecturerId` | Reference to Admin, optional until activation | Identifies the lecturer allocated to the offering. The admin must be active and have the teaching privilege in the owning department. |
| `units` | Positive small integer | Stores the offering’s credit value, copied from the catalog when the offering is created. Catalog changes affect later offerings. |
| `gradingPolicyId` | Reference to GradingPolicy | Pins the score limits and grade bands used for this delivery. The offering keeps its selected policy when a newer policy is activated. |
| `status` | `active` or `inactive`, defaults to `inactive` | Controls whether the offering can accept new registrations. Activation requires a valid lecturer and an eligible curriculum link in the owning department. |

Enforce uniqueness on `(courseId, departmentId, semesterId, academicLevelId)`. Programmes in the same department that link the same course and use the same offering share its roster. A department can allocate a lecturer only within its authority. Use the active grading policy for new offerings and keep prior offerings tied to their original policy after it retires. Course, department, semester, level, units, and grading policy become fixed once the first student registers. Any later lecturer reassignment is audited and updates the offering and its result group together. Reassignment is allowed while results are editable.

## Matriculation and course registration

### MatricNumSystem

PostgreSQL table `matric_num_systems`. One issuance record per student, fixed from issuance until account deletion.

| Property | Type and default | Comment |
| --- | --- | --- |
| `studentId` | Reference to Student, unique | Links the issued number to the student who owns it. |
| `facultyId` | Reference to Faculty | Records the faculty used at issuance, even if the student later transfers. |
| `departmentId` | Reference to Department | Records the department used at issuance. It must belong to the recorded faculty when the number is allocated. |
| `courseOfStudyId` | Reference to CourseOfStudy | Records the programme used at issuance. It must belong to the recorded department when the number is allocated. |
| `issuedYear` | Four-digit integer | Stores the calendar year of issuance in the university’s time zone, Africa/Lagos. Its last two digits form the first segment. |
| `shortId` | Positive database-generated integer, unique | Supplies the final sequence segment of the number. |
| `matricNumber` | Text, unique | Stores the issued identifier in the form `YY/facultyShortId/departmentShortId/courseOfStudyShortId/shortId`, such as `19/1/4/22/1454`. |

Allocate the number once the student has a valid faculty, department, and programme. Allocate the sequence and insert the issuance record in one transaction with a uniqueness constraint on the student. A retry reads the existing number. Issuance links restrict hard deletion of the referenced academic records while the issuance record exists. Account deletion removes the issuance record and its number. Its sequence value is never reused.

### StudentRegisterSemester

PostgreSQL table `student_register_semesters`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `studentId` | Reference to Student | Identifies the student whose term registration and academic history this record holds. |
| `semesterId` | Reference to Semester | Identifies the term for course registration, unit totals, statements, and semester GPA. |
| `academicLevelId` | Reference to AcademicLevel | Snapshots the student’s level at the first successful registration for this semester. |
| `courseOfStudyId` | Reference to CourseOfStudy | Snapshots the programme used to determine course eligibility for this term and to label the historical record. |
| `departmentId` | Reference to Department | Snapshots the department administering the student’s registration for this term. |
| `facultyId` | Reference to Faculty | Snapshots the faculty under which this term’s registration was made. |

Enforce uniqueness on `(studentId, semesterId)`. Create the record on the first successful registration in the term. Its placement fields must agree with one another and remain fixed for that term. A later change to the student’s profile takes effect for future terms. Use this row to serialize concurrent unit-limit checks for the same student and term. Closing a course roster leaves this semester record in place and does not create a second record.

### StudentRegisteredCourse

PostgreSQL table `student_registered_courses`.

| Property | Type and default | Comment |
| --- | --- | --- |
| `studentId` | Reference to Student | Identifies the student enrolled in this course. It must match the student on the semester record. |
| `courseId` | Reference to Course | Identifies the catalog course for history and duplicate prevention, including when a course appears in multiple offerings. It must match the course on the result group’s offering. |
| `studentRegisterSemesterId` | Reference to StudentRegisterSemester | Attaches the enrollment to the student’s term record and its historical academic placement. |
| `resultGroupId` | Reference to ResultGroup | Places the student on the offering’s grading roster and connects the row to the result publication status. |
| `registeredByUserId` | Reference to User | Records who actually submitted the registration. For self-registration, it is the student’s account. If an authorized admin registers on the student’s behalf, it is the admin’s account. |

Enforce uniqueness on `(studentRegisterSemesterId, courseId)`. Enforce that the enrollment and its semester record reference the same student. The result group’s offering must match the enrollment’s course and the term record’s semester, department, and level. The awarding command verifies that the grade band belongs to the offering’s grading policy. Term registration reports use the snapshot fields. Student result queries use the result group’s current approval status before exposing scores or the award.

## Grading and results

### GradingPolicy

PostgreSQL table `grading_policies`. An offering uses one version for its entire grading lifecycle.

| Property | Type and default | Comment |
| --- | --- | --- |
| `version` | Positive integer, unique | Gives each published configuration a stable version for offerings and historical reports. |
| `name` | Text | Describes the grading configuration in admin screens, such as “Standard Five Point Scale”. |
| `maxCaScore` | Positive decimal with up to two fractional digits | Sets the maximum CA mark for offerings using this policy. |
| `maxExamScore` | Positive decimal with up to two fractional digits | Sets the maximum exam mark. The two components must add up to 100. |
| `status` | `draft`, `active`, or `retired`, defaults to `draft` | Allows a policy to be prepared, selected by default for new offerings, or retired while existing offerings keep their reference. |

Allow one active default at a time. Activate a policy and retire the previous default in one transaction after validating all bands. Component limits and bands are editable while the policy is a draft. Publish a new version for any later change.

### GradeSystem

PostgreSQL table `grade_systems`. One row defines a score band within a grading policy.

| Property | Type and default | Comment |
| --- | --- | --- |
| `gradingPolicyId` | Reference to GradingPolicy | Identifies the scale version that owns the band. |
| `grade` | `A`, `B`, `C`, `D`, `E`, or `F` | Supplies the letter shown to the student for an approved score in this band. |
| `minScore` | Decimal from 0 to 100, up to two fractional digits | Sets the lowest total score included in the band. |
| `maxScore` | Decimal from 0 to 100, up to two fractional digits | Sets the highest total score included in the band. |
| `point` | Decimal from 0 to 5, up to two fractional digits | Supplies the grade points per credit unit in GPA and CGPA calculations. |

Enforce one row per `(gradingPolicyId, grade)`. Require `minScore ≤ maxScore` and prohibit overlapping ranges in one policy. On activation require all six bands and complete coverage of every total from 0.00 to 100.00 at two-decimal precision. Validate score components before accepting them. Total score is the sum of CA and exam marks.

### ResultGroup

PostgreSQL table `result_groups`. One group represents the roster and result lifecycle of one offering.

| Property | Type and default | Comment |
| --- | --- | --- |
| `courseOfferingId` | Reference to CourseOffering, unique | Connects the group to one course delivery and supplies its course, owning department, semester, academic level, and grading policy. |
| `lecturerId` | Reference to Admin | Identifies the lecturer responsible for the group. Initialize it from the offering and keep it in sync during an authorized reassignment. |
| `status` | `pending`, `submitted`, `approved`, or `correction_requested`, defaults to `pending` | Tracks grading and review. Pending is the draft state. Approved is the only state that publishes grades to students. |
| `registrationStatus` | `opened` or `closed`, defaults to `opened` | Tracks whether students can join the roster. Once closed, this field cannot return to opened. |
| `registrationClosedAt` | Timestamp with time zone, optional | Records when the lecturer closed the roster. It is required for a closed roster. |
| `registrationClosedByAdminId` | Reference to Admin, optional | Identifies the lecturer who closed registration. It is required for a closed roster. |
| `submittedAt` | Timestamp with time zone, optional | Records when the latest submission was sent for review. |
| `submittedByAdminId` | Reference to Admin, optional | Records the lecturer who made the latest submission, even if the group is reassigned later. |
| `submissionReason` | Text, optional | Records an explanatory note on the latest submission. |
| `approvedAt` | Timestamp with time zone, optional | Records when the latest approval was given. Current publication is determined by status. |
| `approvedByAdminId` | Reference to Admin, optional | Records the admin who gave the latest approval. The same person may have submitted it if they have approval privileges for the department. |
| `approvalReason` | Text, optional | Records an explanatory note on the latest approval. |
| `correctionRequestedAt` | Timestamp with time zone, optional | Records when the most recent request for corrections was made. |
| `correctionRequestedByAdminId` | Reference to Admin, optional | Identifies the admin who made the most recent correction request. |
| `correctionRequestReason` | Text, optional until a correction is requested | Records the feedback the lecturer needs to address before resubmission. |

The first successful registration creates the group and enrollment in the same transaction. The unique offering key prevents concurrent first registrations from creating multiple groups. A group can have an open roster only in the pending state. A closed roster requires both closure fields. Submission, approval, and correction-request states require the corresponding action time and actor, plus a reason for a correction request. These fields summarize the latest action of each kind. The audit history preserves every transition and remains the source for prior review cycles.

### AdminAudit

PostgreSQL table `admin_audit_events`. This is an append-only record of administrative mutation attempts.

| Property | Type and default | Comment |
| --- | --- | --- |
| `action` | Controlled text | Identifies what happened using a stable name from the audit action registry, such as `result.approve` or `admin.role.assign`. |
| `category` | Controlled text | Groups related actions for filtering, such as results, accounts, or academic structure. |
| `actorUserId` | UUID, optional | Identifies the authenticated account behind the attempt. It can be present when authorization was denied before an admin profile could be resolved. |
| `actorAdminId` | UUID, optional | Identifies the resolved admin profile. The event retains this internal ID through account redaction. |
| `targetType` | Controlled text | Identifies the kind of record affected, such as `result_group` or `student_registered_course`. |
| `targetId` | UUID, optional if no target could be resolved | Identifies the affected row. The target type tells the reader which table it belongs to. |
| `outcome` | `succeeded`, `denied`, or `failed` | Distinguishes committed actions from rejected or unsuccessful attempts. |
| `reason` | Controlled text, optional | Records a safe reason code for the outcome, such as insufficient scope or corrections required. Detailed feedback belongs on the result group. |
| `changes` | JSON object, optional | Stores the approved before-and-after fields needed to understand a change, such as score changes on one enrollment or a result status transition. |
| `metadata` | JSON object, optional | Stores bounded context such as the department and offering IDs for a departmental review. |
| `requestId` | Text, optional | Correlates the action with an HTTP request and its structured logs. |
| `traceId` | Text, optional | Correlates the action with a trace when tracing is enabled. |
| `occurredAt` | Timestamp with time zone, defaults to now | Records when the action occurred and orders the audit trail. |

Register every admin mutation with a semantic action and category. The admin guard records recognized denied attempts. An interceptor captures successful and failed HTTP mutations. Result and grade changes write their successful domain events in the same transaction as the change. The interceptor uses that outcome instead of writing a duplicate event. Bulk grading can write one event per changed enrollment linked by the same request ID. If audit recording fails after a separate mutation has already committed, log the audit failure and preserve the mutation’s actual HTTP outcome.

Use action-specific allowlists for `changes` and `metadata`. Record internal IDs, state changes, and the specific grade values needed for result history. Exclude names, email addresses, matriculation numbers, raw feedback, credentials, tokens, IP addresses, user agents, and complete request or response bodies. Actor IDs are stored as values so account redaction requires no audit update. The repository exposes append and read operations, and PostgreSQL rejects updates and deletions. Restrict audit history to admins with audit read privileges. Use cursor pagination with filters for actor, action, category, target, outcome, and date range.

## Workflow rules across tables

### Registration and department ownership

For example, if Computer Science and Mathematics both include `CSC101`, they each have their own `CourseOfStudyCourse` row pointing to the same catalog course. If the programmes belong to different departments, each department has its own `CourseOffering` for the semester and level. Each offering gets its own roster, assigned lecturer, and result group. The student sees the offering for the department in their term placement.

1. Resolve the student from the authenticated account or from an admin with registration authority in the student’s current department. For the first registration, use the student’s current placement and faculty’s current semester. After that, use the placement saved in the semester record. If the departments differ, an admin submitting on the student’s behalf also needs registration authority in the department on the semester record. A student can update permitted personal profile fields. Academic placement after signup is an admin action.
2. Require an active student account, valid matriculation number, active academic placement at a positive study stage, and an active session and semester. Require the selected term to be current for the relevant faculty. Verify that each offering is active, belongs to the student’s department and level, has an active assigned lecturer with teaching authority there, and that its catalog course is active and mapped to the student’s programme.
3. In one PostgreSQL transaction, create or lock the student’s semester record, then lock requested offerings and their result groups in a consistent order. Create missing result groups in that transaction. Reject duplicate course IDs, rosters that are closed, and requests that would exceed the semester’s unit limit. Save the full valid selection together. Registration and roster closure take the same offering and group locks so closure cannot race with an enrollment.
4. Return registered courses and units from the stored enrollments. Build the printable registration summary from the semester record and its enrollments. Build department registration reports from those same records, filtered by the department on the semester record.

### Grading and approval

| Action | Required state and authority | Outcome |
| --- | --- | --- |
| Save marks | The group is pending or has corrections requested. The active assigned lecturer has the teaching privilege in this department. | Valid marks are saved as a draft. The lecturer can enter marks before closing the roster. The roster closes only through the explicit close action. |
| Close registration | The group is pending and the roster is open. The active assigned lecturer has the teaching privilege in this department. | The roster closes permanently and the actor and time are recorded. No further enrollment or replacement batch is allowed. |
| Submit or resubmit | The group is pending or has corrections requested, the roster is closed, and both marks are present for every enrollment. The active assigned lecturer submits. | The group becomes submitted. Scores are locked for review. |
| Approve | The group is submitted. The active admin has `approve_result` for the owning department. | The transaction assigns the grade band to each enrollment, records approval, and publishes the group. The approver may also be the submitting lecturer. |
| Request corrections | The group is submitted. The active admin has review authority in the owning department and supplies feedback. | The group becomes `correction_requested`. The assigned lecturer can edit scores and resubmit. The roster stays closed. |
| Reopen grading | The group is submitted or approved. The active admin has `reopen_result` in the owning department and supplies a reason. | The group becomes pending and the roster stays closed. If it was approved, record the previous scores and awards in the audit trail and clear the current grade awards in the same transaction. Student views show results again after reapproval. |

Lock the offering and result group in the same order when saving marks or changing state. Derive the department from the offering on the server. Confirm the enrollment belongs to the group before writing a mark. Check the actor’s current scope and assignment in the command handler even when the HTTP guard already ran. Record marks, roster closures, submissions, decisions, reopenings, and reassignments in the audit trail. An accepted result correction never adds a student to a closed roster.

The demo policy uses **30 marks for CA and 70 for the exam**. These are proposed seed values. Each version defines its own component maxima and bands.

| Grade | Inclusive total score | Grade points |
| --- | --- | --- |
| A | 70.00–100.00 | 5 |
| B | 60.00–69.99 | 4 |
| C | 50.00–59.99 | 3 |
| D | 45.00–49.99 | 2 |
| E | 40.00–44.99 | 1 |
| F | 0.00–39.99 | 0 |

The backend uses currently approved results for statements, semester GPA, and CGPA. Multiply each approved grade’s points by its registered credit units, add those values, and divide by total approved credit units. Semester GPA uses one term. CGPA uses all terms. Failed attempts contribute zero points and retain their units. A repeat in a later term counts as another attempt. Round only the final displayed value to two decimal places. Return an unavailable GPA when there are no approved units. Grades are awarded against the offering’s pinned policy, so activating a new scale cannot change a historical award.

### Privileges and read models

| Experience | Data and authority |
| --- | --- |
| Student | The authenticated account owns its profile, registrations, and results. The BFF returns available courses, registered courses and unit totals, and approved academic history. Printable registration and result statements use the same access checks. |
| Lecturer | A teaching grant in the offering’s department and the lecturer assignment permit viewing the roster, entering marks, closing registration, and submitting results. Course and student performance summaries are limited to assigned offerings. |
| HOD or departmental admin | Scoped grants cover the enabled actions for the department, such as managing students, lecturer profiles, curriculum, and offerings, viewing course registrations, and reviewing results. The privilege for a write must be available in the affected department. |
| Super Admin | A university-wide assignment provides the privileges for managing faculties, departments, programmes, terms, courses, accounts, and roles, and for viewing university-wide activity and academic reports. |

Check the requested privilege and its scope against the same grant. For example, a read grant for one department and an approval grant for another cannot authorize approval in the first department. The BFF only populates relations present in an endpoint’s allowlist and permitted by the caller’s grants or student ownership. A populated record must also pass its own row scope and publication checks. Admins with multiple assignments use the same account and can access the dashboards their effective grants permit.

### Account deletion and redaction

Lock the account and make deletion idempotent. In one PostgreSQL transaction, set `deletedAt`, replace the email with a unique placeholder under `redacted.invalid`, clear the name and password fields, and advance `authVersion`. For a student account, clear the current placement fields and remove the matriculation issuance row, including its number, sequence value, and issuance context. Preserve historical term records, registrations, and grades under their internal IDs. Deletion applies to the specific account and leaves a separate account with the same original email in the other account type unaffected.

Revoke sessions and remove account PII from caches and any retained exports the application manages. The committed deletion and auth version already block sign-in and protected requests. Retries can finish cache cleanup without repeating the database redaction. Keep direct identifiers out of durable logs and audit events. If mutable feedback contains a direct identifier, redact it while preserving the operational feedback. Use internal IDs for authorized history views and keep the deleted account’s profile and identifiers out of responses.

### Integrity and retention

- Enforce primary keys, foreign keys, uniqueness, enum values, and numeric ranges with named PostgreSQL constraints. Use matching composite references where the related keys are available, such as the enrollment’s student and semester record. Where a rule spans several rows, the owning transaction validates and locks the relevant state. Guard one-way roster closure, immutable term snapshots and published policy data, and issuance records that are fixed until account deletion.
- Restrict hard deletion of academic rows referenced by matriculation, offerings, registrations, or grades. Use deactivation for those records and soft deletion for accounts. The Faculty-to-Department cascade is available only for unused records that satisfy the other references. If an unused placement reference is removed, clear dependent selections in the same operation so an incomplete profile cannot retain a contradictory hierarchy. A scoped role grant must be explicitly revoked before removing its department.
- Index foreign keys used for access and reporting. Prioritize offerings by department, semester, and level, lecturer assignments by lecturer and term, curriculum links by programme and course, enrollment rosters by result group, and student history by student and semester. Index audits by target and occurrence time and by actor and occurrence time. Use the uniqueness constraints for account, registration, and grant lookups.
- Keep synchronous writes that enforce academic and permission rules in PostgreSQL transactions. Use CQRS handlers for writes and sagas for downstream work after commit, such as cache invalidation. In production, state that must survive a process restart remains in PostgreSQL.

## Redis sessions and instrumentation

PostgreSQL owns account state and `authVersion`. Compose runs Redis alongside PostgreSQL and the backend. Redis holds session records for both token types with a TTL matching the token expiry. The key contains the token type, user ID, and token ID. Redis stores session metadata for signed tokens.

| Session property | Stored for | Comment |
| --- | --- | --- |
| `userId` | Access and refresh keys | Links the session record to the issuing account. |
| `jti` | Access and refresh keys | Uniquely identifies the issued token and supports lookup and revocation. |
| `type` | Access and refresh keys | Distinguishes access records from refresh records. Each token is accepted only for its own purpose. |
| `authVersion` | Access and refresh values | Records the PostgreSQL auth version when the token family was issued. |
| `refreshJti` | Access value | Links the access record to its refresh record. Revoking the refresh record invalidates the related access token. |
| `expiresAt` | Access and refresh TTL | Defines the end of validity and the time at which Redis automatically removes the record. |

Verify the token, account status, Redis session record, and current auth version on protected operations. On refresh, claim the old refresh record atomically, then advance the account’s auth version and issue a replacement pair. Serialize changes to the auth version and check the expected version before advancing it so a stale refresh cannot replace a later sign-in or undo revocation. Logout revokes the pair. Session checks fail closed if their backing state is unavailable.

Use structured logging, metrics, and tracing. Development and staging emit logs only. Request IDs are still available for audit correlation in those environments. Code comments should explain decisions such as scoped grant matching, irreversible roster closure, and versioned grades near the logic that enforces them.

## Approved decisions

| Decision | Behavior |
| --- | --- |
| Offering boundaries | One offering per course, department, term, and academic level. Programmes in the same department can share that offering if both map to the course. Different departments always have separate rosters and results. |
| Result lifecycle | One result group per offering. Closure ends registration permanently. An authorized reopening of approved grades withdraws publication until the group is approved again. |
| Grading and repeats | Seed the 30/70 five-point policy above. Count every approved attempt in its term and in cumulative calculations, including failed attempts and later repeats. |
| Account and identity retention | Issue a matriculation number from the student’s original placement. On account deletion, remove the issuance record and redact account PII. Release the original email and retain academic and audit history under internal IDs. |
| Administrative course registration | Allow an admin with an explicit registration privilege in the student’s department to act on the student’s behalf. Apply the same eligibility, unit, and roster rules and record the actor. |
