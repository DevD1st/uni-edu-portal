# UEMP frontend contributor guide

## Workspace

- Keep the Next.js student portal in `apps/student` and the React/Vite staff portal in `apps/admin`. Run workspace commands from `frontend/` with the pinned pnpm version. Keep one frontend lockfile and pin direct dependencies.
- Shared code lives in `packages/*` and uses the `@uemp/*` scope with `workspace:*`. Applications may import public package exports. Packages never import apps or route implementations. Avoid dependencies between app internals.
- Keep route composition, feature copy, API endpoint adapters, authorization, and product workflows inside the owning app. Group new product modules under `src/features/<domain>`. Extract shared behavior when both apps can use the same contract.
- Keep route files focused on composing the page. Put domain UI in the feature’s `components/` directory and server-only data access in its `server/` directory. Keep app-specific shared presentation inside the portal feature.
- Keep TypeScript strict. Treat API payloads, URL parameters, storage, and environment variables as untrusted. Use explicit types and validation at boundaries. Keep generated OpenAPI types in `packages/api-contracts` and regenerate them from the backend contract after endpoint changes.

## Design and accessibility

- Read `docs/design-system.md` before changing visual values, shared components, or shell behavior. Use Source Sans 3 from the theme package and use its semantic tokens in both apps.
- Use the review questions and page/component inventory in `docs/ui-review.md` for UI work. Review purpose, information completeness, hierarchy, grouping, next actions, feedback, responsive layouts, and accessibility together; keep the inventory current as screens change. Verify composed pages visually as well as checking individual primitives.
- Use the shared theme, Tailwind v4 semantic utilities, and authored CSS for component state or layout. Add a token when a value has a shared role. Keep contrast, keyboard operation, touch, focus, wrapping, and reduced motion in the same change as the UI.
- Design narrow first. Check 320, 390, 768, 1024, and 1440 CSS px. Preserve access to actions and form help when panels stack. Keep intentional table scrolling inside a labeled region. Verify both light and dark modes.
- Present loading, empty, error, restricted, and success states where a feature fetches data. Use readable field and page errors. Pair status colors with labels.

## Access and sessions

- The API authorizes every operation. The staff app uses the current grants from `/v1/admin/admins/me/authorization` for navigation, direct routes, and controls. Treat role names as labels. Match each privilege to its actual department or university-wide grant. Match assignment and result state when the backend requires them. Revalidate grants after a permission change and after a denied operation.
- Dashboard cards use their owning API and mount only with the required privileges. Teaching assignments do not confer departmental reporting. Keep previews clearly distinct from complete totals, and validate dashboard URL filters against authorized choices. Student academic summaries remain server-rendered and use published averages from the API.
- Show existing student placement names from the authenticated profile. Public academic references contain active signup choices and cannot identify every previously assigned record after deactivation.
- The student app stores access/refresh tokens and their expiries in HTTP-only, SameSite cookies, with Secure enabled for an HTTPS public origin. Only route handlers may rotate or clear these cookies. Server components read them and send expired or rejected sessions through the same-origin renewal route before rendering again. Keep return destinations restricted to student routes. Browser code calls same-origin APIs and never receives token values. Coordinate cookie-authenticated browser requests across tabs so single-use refreshes cannot race. Frontend applications use the HTTP API exclusively; infrastructure and token revocation belong to Nest.
- The admin app owns a validated tab session in sessionStorage. Refresh five minutes before access expiry, share one refresh in flight, and retry an unauthorized request once. Keep staff credentials isolated by tab. A duplicated tab with a stale pair must reauthenticate rather than replace another tab's credentials. Clear local credentials in a sign-out finally block even if the API fails. Never let a delayed response or refresh overwrite or clear a later sign-in. Clear stale session and protected data after revocation. Never log or expose tokens or raw server errors.
- Keep secrets out of public environment variables, fixtures, screenshots, and commits. Use no-store for protected data. Prefer safe contract errors and request IDs when troubleshooting. Reuse the existing demo backend to exercise real role and scope behavior.
- Registration summaries and result statements open authenticated print views in a separate tab. Reuse the owning feature's validated server reads and course tables, retain semester snapshots and approved-only results, and keep portal navigation and controls off paper. Check narrow screens, dark mode, A4 column fitting, access denial, and session renewal when changing print behavior.

## Verification

- Run `pnpm check` for formatting, lint, strict type checks, targeted tests, and both production builds. Run `pnpm test:e2e` against the demo backend for routing, sign-in, and responsive regression checks. Add coverage for new permission rules and behavior that can regress.
- Keep setup notes and design examples current. Commit source and the generated contract types. Exclude build output, caches, browser reports, dependencies, and local environment files.
- Keep the shared Dockerfile's pnpm version aligned with `packageManager`. Docker student builds set `UEMP_STANDALONE=1` and trace workspace dependencies; host builds keep their normal output. The student server uses private Compose addresses at runtime, while the staff browser API origin is a public build argument. Never copy local environment files or backend secrets into frontend images. Keep production-container E2E mode separate from Vite-only error injection tests.
- Use the repository's single `docker-compose.yaml` for full-stack or backend-only startup. Its initialization job applies migrations and seeds a fresh demo database automatically before the API and portals start; subsequent startup preserves seeded records. Do not add a separate Compose overlay for frontend services or demo initialization.
- Plain Compose commands load the shared root `.env` automatically and use the `uemp-demo` project name. Keep backend secrets in that ignored file, outside frontend build contexts. Frontend `.env.local` files remain host-development settings only; frontend images receive only their explicitly declared application values.
- Keep the [staff workflow guide](docs/staff-workflows.md) current when a workspace, permission, or result state changes. Preserve unsaved marks across roster/marks tabs, and disable any pagination or refresh that would remount an editor with unsaved changes. Test combined roles and cross-department denials against a disposable backend.
- Use the data router's blocker for unsaved marks and guard sign-out before revoking credentials. Keep native unload warnings conditional on dirty/pending state. Do not allow departures during a pending save or let a draft block an authentication revocation. Keep rendering recovery generic and exercise it through test-only component injection.
