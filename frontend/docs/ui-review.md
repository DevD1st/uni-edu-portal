# UI review and refinement

The review follows the [design-system rubric](design-system.md#review-questions) and examines the shared components, student pages, staff workspaces, their details and dialogs, and the states between actions. A successful operation is only one part of the review: its information, visual hierarchy, arrangement, feedback, keyboard behavior, and small-screen presentation must also make sense.

## Questions used for each element

- **Purpose and context:** Can someone tell where they are, whose record they are viewing, and which semester, department, or scope applies? Does the title describe the task rather than its implementation?
- **Completeness:** Are the identity, status, units, limits, counts, saved values, and next steps needed for this decision present? Are unavailable values distinguished from zero, and are previews distinguished from totals?
- **Order and grouping:** Does the page follow the user's decision sequence? Are filters attached to their records, related fields grouped, and details placed beside the actions they inform?
- **Hierarchy and emphasis:** Is there a clear heading and primary action? Do secondary, destructive, disabled, and pending actions have appropriate emphasis? Are dashboard values easier to scan than ordinary record metadata?
- **Visual quality:** Are type, line lengths, spacing, alignment, icons, corners, surfaces, and borders consistent? Is the layout balanced when only some privilege-dependent panels are visible? Does every decorative element have a purpose?
- **Language:** Are labels and statuses readable without knowing API enum values? Are dates, numbers, grades, and credit units formatted consistently? Does help explain the decision or constraint at the point of use?
- **Interactions:** Can someone select, search, review, save, cancel, retry, or leave without losing context? Do search and pagination preserve the correct state? Are saved values and unsaved edits distinguished?
- **Feedback and recovery:** Do loading, empty, success, error, restricted, and not-found states explain what happened and offer an appropriate next step? Can one failed summary recover without hiding the rest of the page?
- **Responsiveness:** Does the layout work at 320, 390, 768, 1024, and 1440 CSS pixels? Do long labels wrap naturally? Can wide tables scroll inside their own region while the page remains within the viewport? Are dialog actions reachable in a short viewport?
- **Accessibility:** Are labels stable, field help and errors associated, focus visible, targets comfortable, status paired with text, and dialogs usable with a keyboard? Do both themes retain readable contrast and reduced-motion behavior?
- **Trust and safeguards:** Does each panel use the correct privileges and department scope? Are published results the only results visible to students? Do confirmation, pending, session, and unsaved-marks protections still work?
- **Paper and reuse:** Do print views include the necessary record context and every column without portal controls? Does each reusable element belong to the shared system or its owning feature, and does it use semantic tokens rather than isolated visual values?

## Shared foundation

The [component decisions](design-system.md#shared-component-decisions) cover theme tokens, Source Sans 3, stacks and grids, CSS layering, buttons and icon buttons, input/select/checkbox controls, badges and banners, surfaces and page headings, description lists, data tables, resource states, pagination, dialogs and drawers, brand and navigation, account/theme controls, authentication layouts, and links/cards.

The review found that `u-stack` was used throughout the applications without a matching style rule. It now supplies consistent spacing and safe shrinking. Shared styles use the components layer so responsive visibility utilities remain authoritative. Required markers preserve the actual label text, and password actions are anchored to the input rather than its helper or error copy. Shared readiness handling keeps navigation, theme, editable student controls, and print actions inactive until their handlers are attached. Credential and profile forms also use a POST fallback; native submission cannot put those field values in a URL.

Both browser entrypoints include the same campus tab mark as the portal identity. Production delivery checks verify that those icon assets load correctly. Reduced-motion styling also limits animations to one short iteration so a loading spinner cannot continue looping when motion is reduced.

## Verification

Use `pnpm check` for formatting, lint, strict types, focused tests, and production builds. Use the real-backend browser suite on a disposable demo for signup, registration, marks, review, publication, roles, reports, audit, error recovery, unsaved work, and session behavior.

`e2e/ui-review.spec.ts` adds regressions for exact password labels and visibility controls, form readiness before JavaScript, both authentication themes and responsive layouts, preservation of selected courses while searching and clearing, a locked confirmation during registration, and all nine academic setup categories. The profile regression also checks inactive server-rendered controls before hydration. Existing printing tests cover self-contained paper views, mobile table access, authentication, and published-only statements. Browser review captures desktop and phone layouts for manual inspection in addition to automated overflow and accessibility checks.

The complete development-mode browser run passed 37 tests, including workflow, permission, session, error-recovery, unsaved-work, print, and responsive cases. Its two environment-specific checks are the production container delivery test and the opt-in live-expiry fixture. Final focused checks also cover the added readiness safeguards. `pnpm check` validates both production builds alongside formatting, lint, strict types, and the shared/client privilege tests.
